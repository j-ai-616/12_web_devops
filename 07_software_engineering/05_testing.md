# 소프트웨어 테스트

## 학습 목표

- 테스트의 목적과 기본 원칙을 설명할 수 있다.
- 블랙박스 테스트와 화이트박스 테스트를 구분할 수 있다.
- 객체지향 테스트의 대상과 테스트 대역을 설명할 수 있다.
- 단위, 통합, 시스템과 인수 테스트의 차이를 설명할 수 있다.
- 테스트 계획, 실행, 결함과 결과를 관리할 수 있다.
- 목적에 맞는 테스트 자동화 도구를 선택할 수 있다.

## 1. 테스트란 무엇인가

소프트웨어 테스트는 예상한 조건에서 실제 결과가 요구사항과 일치하는지 확인하고 결함의 존재를 발견하는 활동이다.

테스트는 결함이 전혀 없음을 완전히 증명하지 못한다. 가능한 모든 입력과 실행 환경을 검사하기 어렵기 때문이다. 따라서 발생 가능성과 피해가 큰 위험을 우선해서 확인한다.

## 2. 오류, 결함과 실패

```text
사람의 오류
  -> 요구사항·설계·코드의 결함
  -> 특정 조건에서 실행
  -> 사용자에게 관찰되는 실패
```

- 오류(Error)는 사람이 잘못 판단하거나 작업한 행위이다.
- 결함(Defect)은 잘못된 요구사항, 설계나 코드에 남은 문제이다.
- 실패(Failure)는 실행 중 실제 결과가 예상 결과와 달라진 현상이다.

예를 들어 개발자가 세율 계산식을 잘못 이해한 것은 오류이고, 잘못된 계산식이 코드에 들어간 것은 결함이다. 특정 주문에서 최종 금액이 틀리게 표시되는 것은 실패이다.

## 3. 테스트와 디버깅

- 테스트는 실패가 존재하는지 발견하고 재현하는 활동이다.
- 디버깅은 실패의 원인을 찾아 코드를 수정하는 활동이다.

테스트가 실패했을 때 기대값을 실제 오류 결과에 맞춰 바꾸면 안 된다. 요구사항, 테스트와 구현 중 무엇이 잘못되었는지 먼저 판단해야 한다.

## 4. 테스트의 기본 원칙

### 테스트는 결함의 존재를 보여 준다

테스트가 성공해도 검사하지 않은 조건에 결함이 남아 있을 수 있다.

### 완전한 테스트는 불가능하다

입력, 상태, 운영체제, 네트워크와 사용자 행동의 모든 조합을 검사하기 어렵다. 위험과 우선순위에 따라 테스트 범위를 정한다.

### 테스트는 일찍 시작할수록 좋다

요구사항과 설계 단계에서도 검토와 시나리오 테스트를 수행할 수 있다. 초기에 발견한 결함은 수정 범위가 작다.

### 결함은 특정 영역에 집중된다

복잡하고 자주 변경되며 여러 기능과 연결된 부분에서 결함이 많이 발생하는 경향이 있다. 결함 기록을 이용해 집중적으로 검사한다.

### 같은 테스트만 반복하면 새로운 결함을 놓친다

기능과 위험이 바뀌면 테스트 데이터와 시나리오도 갱신해야 한다.

### 테스트는 상황에 따라 달라진다

의료 시스템, 게임과 내부 관리 도구는 위험과 품질 기준이 다르다. 동일한 테스트 방식과 수준을 모든 시스템에 적용하지 않는다.

## 5. 테스트 케이스

테스트 케이스는 특정 기능을 검사하기 위한 조건, 입력, 절차와 예상 결과를 정리한 것이다.

| 항목 | 설명 |
| --- | --- |
| ID | 테스트를 식별하는 번호 |
| 연결 요구사항 | 무엇을 검증하는 테스트인지 표시한다 |
| 목적 | 확인하려는 위험이나 기능이다 |
| 사전 조건 | 실행 전에 준비되어야 하는 상태이다 |
| 입력 | 테스트에 사용할 데이터이다 |
| 절차 | 수행할 행동과 순서이다 |
| 예상 결과 | 성공으로 판단할 수 있는 결과이다 |
| 실제 결과 | 실행 후 관찰한 결과이다 |
| 상태 | 성공, 실패, 차단 등으로 기록한다 |

### 예시

| 항목 | 내용 |
| --- | --- |
| ID | TC-LOGIN-03 |
| 연결 요구사항 | FR-LOGIN-01 |
| 목적 | 잘못된 비밀번호로 로그인할 수 없는지 확인한다 |
| 사전 조건 | 활성 상태의 계정이 존재한다 |
| 입력 | 올바른 이메일, 잘못된 비밀번호 |
| 절차 | 로그인 화면에서 값을 입력하고 로그인한다 |
| 예상 결과 | 로그인이 거부되고 비밀번호 오류 메시지가 표시된다 |

예상 결과는 "정상 동작한다"가 아니라 관찰할 수 있는 값과 상태로 작성한다.

## 6. 블랙박스 테스트

### 블랙박스 테스트의 개념

블랙박스 테스트는 내부 코드를 보지 않고 입력과 출력 계약을 기준으로 검사한다. 요구사항, API 명세와 사용자 관점의 동작을 검증하는 데 적합하다.

```text
입력 -> [내부 구현은 고려하지 않음] -> 출력
```

대표적인 설계 기법은 동등 분할, 경곗값 분석, 결정 테이블과 상태 전이 테스트이다.

### 동등 분할

비슷하게 처리될 것으로 예상되는 입력을 같은 그룹으로 나누고 대표값을 선택한다.

회원 가입 나이가 14세 이상 100세 이하라고 가정한다.

| 입력 그룹 | 대표값 | 예상 결과 |
| --- | --- | --- |
| 14~100 | 30 | 허용 |
| 13 이하 | 10 | 거부 |
| 101 이상 | 120 | 거부 |
| 숫자가 아닌 값 | `abc` | 형식 오류 |
| 값 없음 | 빈 값 | 필수 입력 오류 |

같은 그룹의 모든 값을 검사하지 않고 대표값을 사용해 테스트 수를 줄인다.

### 경곗값 분석

결함은 범위의 시작과 끝, 바로 이전과 바로 다음 값에서 자주 발생한다.

14세 이상 100세 이하 조건의 경곗값은 다음과 같다.

```text
13, 14, 15, 99, 100, 101
```

동등 분할의 대표값만 사용하면 `>=`와 `>`를 잘못 사용한 결함을 놓칠 수 있다. 경곗값 분석을 함께 사용한다.

### 결정 테이블

여러 조건의 조합에 따라 결과가 달라질 때 사용한다.

| 로그인 | 관리자 권한 | 계정 활성 | 관리자 화면 접근 |
| --- | --- | --- | --- |
| 아니오 | 무관 | 무관 | 거부 |
| 예 | 아니오 | 예 | 거부 |
| 예 | 예 | 아니오 | 거부 |
| 예 | 예 | 예 | 허용 |

조건 수가 많으면 가능한 조합이 급격히 늘어난다. 결과에 영향을 주지 않는 조건은 무관으로 묶고 위험이 큰 조합을 우선한다.

### 상태 전이 테스트

객체의 현재 상태와 사건에 따라 다음 상태가 달라질 때 사용한다.

```text
작성 중 --제출--> 제출 완료
제출 완료 --승인--> 승인
제출 완료 --반려--> 반려
반려 --수정--> 작성 중
승인 --수정--> 허용하지 않음
```

확인할 내용은 다음과 같다.

- 허용된 상태 전이가 정상적으로 동작하는가
- 금지된 전이를 거부하는가
- 전이 후 상태와 부가 데이터가 올바른가
- 같은 사건이 반복되었을 때 결과가 올바른가

### 유스케이스 테스트

사용자가 목표를 달성하는 전체 흐름을 기준으로 테스트한다.

```text
상품 검색
  -> 장바구니 추가
  -> 배송지 입력
  -> 결제
  -> 주문 완료 확인
```

기본 흐름뿐 아니라 재고 부족, 결제 거절과 배송지 오류 같은 대안 흐름도 확인한다.

## 7. 화이트박스 테스트

### 화이트박스 테스트의 개념

화이트박스 테스트는 코드의 조건, 분기와 실행 경로를 기준으로 검사한다. 내부 구조를 이용해 누락된 테스트 경로를 찾는다.

### 구문 커버리지

코드의 각 실행 구문이 한 번 이상 실행되었는지 측정한다.

```python
def shipping_fee(amount: int) -> int:
    if amount >= 50_000:
        return 0
    return 3_000
```

`amount=60_000`만 검사하면 무료 배송 구문은 실행되지만 유료 배송 반환문은 실행되지 않는다.

### 분기 커버리지

조건문의 참과 거짓 분기가 각각 실행되었는지 측정한다.

위 함수에는 다음 두 테스트가 필요하다.

- `amount=50_000`이면 `0`을 반환한다.
- `amount=49_999`이면 `3_000`을 반환한다.

분기 커버리지는 모든 조합과 업무 요구사항을 보장하지 않는다. 코드 구조를 기준으로 테스트 누락을 찾는 보조 지표이다.

### 조건 커버리지

복합 조건의 각 개별 조건이 참과 거짓을 모두 가지는지 확인한다.

```python
def can_download(is_paid: bool, is_active: bool) -> bool:
    return is_paid and is_active
```

두 조건의 조합은 다음과 같다.

| 결제 여부 | 계정 활성 | 결과 |
| --- | --- | --- |
| 참 | 참 | 참 |
| 참 | 거짓 | 거짓 |
| 거짓 | 참 | 거짓 |
| 거짓 | 거짓 | 거짓 |

### 경로 테스트

여러 분기와 반복문을 거치는 실행 경로를 검사한다. 코드가 복잡해지면 가능한 경로 수가 매우 많아지므로 모든 경로보다 위험한 경로와 독립 경로를 선택한다.

커버리지를 높이기 위해 테스트를 작성하는 것이 아니라 중요한 동작을 검사한 뒤 커버리지로 놓친 코드가 있는지 확인한다.

## 8. 객체지향 테스트

### 객체지향 테스트의 대상

객체지향 프로그램에서는 메서드의 반환값뿐 아니라 객체의 상태, 계약과 협력을 확인한다.

- 생성 직후 객체가 유효한 상태인가
- 메서드 실행 후 상태가 올바르게 변하는가
- 잘못된 상태 전이를 거부하는가
- 상위 타입의 계약을 하위 타입도 지키는가
- 협력 객체에 올바른 메시지를 전달하는가
- 예외가 발생해도 객체가 일관된 상태를 유지하는가

### 상태 기반 테스트

메서드 실행 전후 객체의 상태를 비교한다.

```python
import unittest


class OrderTest(unittest.TestCase):
    def test_cancel_changes_status(self):
        order = Order(total_amount=10_000)

        order.cancel()

        # 취소 동작 이후 주문 상태가 변경되었는지 확인한다.
        self.assertEqual(order.status, "cancelled")
```

### 상호작용 기반 테스트

결과 상태보다 협력 객체가 올바르게 호출되었는지 확인한다.

```python
import unittest
from unittest.mock import Mock


class OrderServiceTest(unittest.TestCase):
    def test_place_order_requests_payment(self):
        payment_gateway = Mock()
        service = OrderService(payment_gateway)

        service.place_order(amount=10_000)

        # 결제 객체가 정확한 금액으로 한 번 호출되었는지 확인한다.
        payment_gateway.pay.assert_called_once_with(10_000)
```

내부 구현과 지나치게 결합된 호출 순서까지 검사하면 리팩터링할 때 테스트가 쉽게 깨질 수 있다. 객체 사이의 중요한 계약만 확인한다.

### 테스트 대역

외부 API, 데이터베이스, 시간과 네트워크처럼 결과를 통제하기 어렵거나 느린 의존성을 테스트 대역으로 바꿀 수 있다.

| 종류 | 역할 |
| --- | --- |
| Dummy | 전달만 하고 실제로 사용하지 않는다 |
| Stub | 미리 정한 값을 반환한다 |
| Fake | 단순하지만 동작 가능한 구현을 제공한다 |
| Spy | 호출 정보를 기록한다 |
| Mock | 예상한 호출과 인자를 검증한다 |

테스트 대역을 많이 사용하면 실제 구성 요소 사이의 연결 오류를 놓칠 수 있다. 단위 테스트와 통합 테스트의 균형이 필요하다.

## 9. 통합 및 시스템 테스트

### 테스트 수준

### 단위 테스트

함수, 클래스와 작은 모듈을 독립적으로 검사한다. 빠르고 실패 원인을 찾기 쉽다.

### 통합 테스트

여러 구성 요소가 정해진 계약대로 연결되는지 검사한다.

- API와 데이터베이스 연결
- 서비스와 외부 결제 Adapter 연결
- 웹 라우터와 Controller 연결
- 메시지 발행자와 소비자 연결

### 시스템 테스트

배포된 전체 시스템을 외부 사용자 관점에서 검사한다. 실제와 유사한 네트워크, 데이터베이스와 실행 환경을 포함한다.

### 인수 테스트

관계자가 합의한 인수 조건을 만족하는지 확인한다. 기술적으로 동작해도 업무 목적을 충족하지 못하면 인수 테스트는 실패할 수 있다.

### 통합 방식

### 빅뱅 통합

모든 구성 요소를 한꺼번에 연결한 뒤 검사한다. 준비는 단순하지만 실패 원인을 찾기 어렵다.

### 상향식 통합

하위 모듈부터 결합하며 위로 올라간다. 하위 기능을 일찍 검증할 수 있지만 상위 흐름을 확인하려면 Driver가 필요할 수 있다.

### 하향식 통합

상위 흐름부터 시작해 하위 모듈을 연결한다. 주요 사용자 흐름을 일찍 볼 수 있지만 준비되지 않은 하위 모듈을 Stub으로 대체해야 한다.

### 점진적 통합

작은 단위로 연결하고 매 단계 회귀 테스트를 실행한다. 실패 원인을 좁히기 쉽다.

### 시스템 테스트의 종류

| 종류 | 확인 내용 |
| --- | --- |
| 기능 테스트 | 요구한 기능과 업무 흐름이 동작하는가 |
| 성능 테스트 | 응답 시간, 처리량과 자원 사용량이 기준을 만족하는가 |
| 부하 테스트 | 예상 부하에서 안정적으로 동작하는가 |
| 스트레스 테스트 | 한계를 넘었을 때 어떻게 실패하고 복구하는가 |
| 보안 테스트 | 인증, 권한과 입력 검증이 올바른가 |
| 복구 테스트 | 장애와 백업 이후 복구할 수 있는가 |
| 호환성 테스트 | 지원 환경에서 동작하는가 |
| 사용성 테스트 | 사용자가 목표를 효율적으로 달성할 수 있는가 |

### 테스트 피라미드

```text
            시스템·UI 테스트
               적은 수
         -------------------
              통합 테스트
               중간 수
         -------------------
               단위 테스트
                많은 수
```

빠르고 격리된 단위 테스트를 많이 두고, 느리고 환경 의존적인 시스템 테스트는 핵심 흐름에 집중한다. 모든 테스트를 브라우저에서만 확인하면 실행 시간이 길고 실패 원인을 찾기 어렵다.

## 10. 테스트 관리

### 테스트 계획

테스트 계획은 무엇을 어떤 기준으로 언제까지 검사할지를 정한다.

포함할 내용은 다음과 같다.

- 테스트 목적과 범위
- 제외 범위와 이유
- 대상 요구사항과 위험
- 테스트 수준과 기법
- 테스트 환경과 데이터
- 역할과 일정
- 시작 조건과 종료 조건
- 결과와 결함 보고 방식

### 위험 기반 테스트

모든 기능에 같은 수준의 테스트를 적용하지 않는다. 발생 가능성과 실패 영향이 큰 항목을 우선한다.

| 발생 가능성 | 실패 영향 | 우선순위 |
| --- | --- | --- |
| 높음 | 높음 | 최우선 |
| 높음 | 낮음 | 중간 |
| 낮음 | 높음 | 높음 |
| 낮음 | 낮음 | 낮음 |

결제, 개인정보 삭제와 권한 검사는 실패 영향이 크므로 경계와 예외를 집중적으로 검사한다.

### 테스트 환경과 데이터

테스트 환경은 실제 운영과 가능한 한 중요한 조건이 같아야 한다.

- 운영과 같은 주요 소프트웨어 버전
- 네트워크와 권한 구조
- 외부 서비스의 테스트 환경
- 개인정보가 제거된 테스트 데이터
- 반복 실행 후 원래 상태로 복구하는 방법

테스트는 가능한 한 필요한 데이터를 스스로 만들고 정리해야 한다. 다른 테스트의 실행 순서와 남은 데이터에 의존하면 결과가 불안정해진다.

### 결함 관리

결함 기록에는 다음 정보가 필요하다.

- 결함 ID와 제목
- 발견한 버전과 환경
- 재현 절차
- 예상 결과와 실제 결과
- 화면, 로그와 오류 메시지
- 심각도와 우선순위
- 담당자와 현재 상태
- 수정한 버전과 재검사 결과

### 심각도와 우선순위

- 심각도는 결함이 시스템과 사용자에게 미치는 영향이다.
- 우선순위는 언제 수정해야 하는지에 대한 업무상 순서이다.

화면의 오탈자는 심각도는 낮지만 출시 첫 화면이라면 우선순위가 높을 수 있다.

### 테스트 결과와 지표

대표적인 지표는 다음과 같다.

- 계획한 테스트 중 실행한 비율
- 성공, 실패와 차단된 테스트 수
- 요구사항별 테스트 적용 여부
- 심각도별 미해결 결함 수
- 코드 커버리지
- 자동화 테스트 실행 시간과 불안정 테스트 수

지표 하나만으로 품질을 판단하지 않는다. 커버리지가 높아도 잘못된 요구사항과 빠진 검증은 발견하지 못할 수 있다.

## 11. 테스트 자동화

### 자동화가 적합한 테스트

- 반복 실행할 가치가 있다.
- 성공과 실패 기준이 명확하다.
- 실행 결과가 사람의 주관에 크게 의존하지 않는다.
- 환경과 데이터를 반복해서 준비할 수 있다.
- 자주 실행해야 하는 회귀 테스트이다.

사용성 평가와 새로운 결함을 탐색하는 테스트처럼 사람의 관찰이 중요한 활동은 자동화만으로 대체하기 어렵다.

### 테스트 자동화 도구

| 목적 | 도구 예시 |
| --- | --- |
| Python 단위 테스트 | `unittest`, `pytest` |
| Java 단위 테스트 | JUnit |
| JavaScript 단위 테스트 | Jest, Vitest |
| 코드 커버리지 | coverage.py, JaCoCo, Istanbul |
| 웹 UI 테스트 | Playwright, Selenium, Cypress |
| API 테스트 | Postman/Newman, REST Assured |
| 성능 테스트 | JMeter, k6, Locust |
| 정적 분석 | Ruff, ESLint, SonarQube |
| CI 실행 | GitHub Actions, GitLab CI, Jenkins |

도구의 수보다 어떤 위험을 어떤 수준에서 검사하는지가 먼저이다.

### Python 단위 테스트 예제

`price.py` 파일에 다음 함수를 작성했다고 가정한다.

```python
def shipping_fee(amount: int) -> int:
    if amount < 0:
        raise ValueError("주문 금액은 0 이상이어야 한다")
    if amount >= 50_000:
        return 0
    return 3_000
```

`test_price.py` 파일에 다음 테스트를 작성한다.

```python
import unittest

from price import shipping_fee


class ShippingFeeTest(unittest.TestCase):
    def test_free_shipping_at_boundary(self):
        # 무료 배송이 시작되는 경곗값을 확인한다.
        self.assertEqual(shipping_fee(50_000), 0)

    def test_paid_shipping_below_boundary(self):
        # 경곗값 바로 아래에서는 배송비가 발생하는지 확인한다.
        self.assertEqual(shipping_fee(49_999), 3_000)

    def test_negative_amount_is_rejected(self):
        # 유효하지 않은 음수 주문 금액을 거부하는지 확인한다.
        with self.assertRaises(ValueError):
            shipping_fee(-1)


if __name__ == "__main__":
    unittest.main()
```

터미널에서 다음 명령으로 실행한다.

```bash
# 현재 디렉터리에서 이름이 test로 시작하는 테스트 파일을 자동으로 찾는다.
python -m unittest discover -v

# 특정 테스트 파일만 자세한 출력과 함께 실행한다.
python -m unittest test_price -v

# 특정 테스트 클래스의 메서드 하나만 실행한다.
python -m unittest test_price.ShippingFeeTest.test_free_shipping_at_boundary -v
```

`python -m unittest`는 현재 선택된 Python 인터프리터에서 표준 라이브러리의 테스트 실행기를 시작한다. `-v`는 각 테스트 이름과 결과를 자세히 출력한다.

### 자동화 파이프라인

```text
코드 변경
  -> 정적 분석
  -> 단위 테스트
  -> 통합 테스트
  -> 빌드
  -> 시스템 테스트
  -> 배포 승인
```

앞 단계가 성공해야 다음 단계로 넘어가는 조건을 품질 게이트라고 한다. 테스트가 실패한 결과물을 배포하지 않도록 자동화한다.

### 불안정한 테스트

같은 코드에서 실행할 때마다 성공과 실패가 달라지는 테스트를 불안정한 테스트라고 한다.

주요 원인은 다음과 같다.

- 실행 순서에 의존한다.
- 시간과 시간대에 의존한다.
- 네트워크와 외부 서비스 상태에 의존한다.
- 테스트 데이터가 정리되지 않는다.
- 비동기 작업의 완료를 고정된 대기 시간으로 추측한다.

실패한 테스트를 무조건 다시 실행해 통과시키지 않는다. 원인을 찾아 결정적인 조건으로 바꾼다.

### 회귀 테스트

회귀는 새로운 변경으로 이전에 정상 동작하던 기능이 실패하는 현상이다. 변경한 기능의 테스트뿐 아니라 기존 전체 테스트를 다시 실행해야 한다.

```text
새 기능 테스트 성공
  + 기존 기능 테스트 성공
  = 변경에 따른 회귀 위험 감소
```

자동화된 회귀 테스트는 변경을 빠르게 검증하는 안전망이지만 잘못된 설계를 자동으로 바로잡지는 않는다.

## 핵심 정리

- 테스트는 결함이 없음을 증명하는 활동이 아니라 위험한 결함을 발견하는 활동이다.
- 블랙박스 테스트는 입력과 출력 계약을, 화이트박스 테스트는 코드 구조와 경로를 기준으로 한다.
- 단위, 통합과 시스템 테스트는 발견하는 문제의 범위가 다르다.
- 테스트 계획, 데이터, 환경, 결함과 결과를 함께 관리해야 한다.
- 자동화 도구는 테스트 목적과 위험에 맞게 선택하며 품질 게이트에 연결한다.

## 확인 문제

1. 블랙박스 테스트와 화이트박스 테스트의 차이를 설명한다.
2. 단위 테스트만으로 시스템 품질을 확인할 수 없는 이유를 설명한다.
3. 코드 커버리지가 높아도 결함이 남을 수 있는 이유를 설명한다.
4. 테스트 자동화가 적합하지 않은 활동을 한 가지 작성한다.
5. 불안정한 테스트를 단순 재실행으로 처리하면 안 되는 이유를 설명한다.

5. 재실행으로 통과시키면 순서, 시간, 데이터와 외부 환경에 대한 실제 의존성이 남아 결과를 신뢰할 수 없기 때문이다.
