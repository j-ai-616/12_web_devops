# 요구사항 개발과 관리

## 학습 목표

- 요구사항의 의미와 종류를 구분할 수 있다.
- 도메인을 분석하고 문제의 범위를 설정할 수 있다.
- 요구사항을 추출하고 검증 가능한 문장으로 문서화할 수 있다.
- 요구사항 합의, 형상관리와 이력추적의 목적을 설명할 수 있다.

## 1. 요구사항이란 무엇인가

요구사항은 시스템이 제공해야 하는 기능과 반드시 지켜야 하는 조건이다. 단순한 아이디어나 요청을 그대로 기록한 문장이 아니라 개발, 테스트와 인수 여부를 판단할 수 있는 기준이다.

다음 문장은 요청이지만 아직 요구사항으로 사용하기 어렵다.

> 검색이 빠르고 편리해야 한다.

누가 사용하는지, 무엇을 검색하는지, 어느 정도가 빠른지 알 수 없기 때문이다. 다음과 같이 구체화하면 검증할 수 있다.

> 로그인한 사용자는 강좌명과 카테고리명으로 강좌를 검색할 수 있어야 한다. 정상적인 네트워크 환경에서 검색 결과는 2초 안에 표시되어야 한다.

요구사항은 설계와 구현의 출발점이며 테스트의 기준이기도 하다.

```text
사용자의 문제
  -> 요구사항
  -> 설계
  -> 구현
  -> 테스트
  -> 인수
```

## 2. 요구사항의 종류

### 기능 요구사항

시스템이 제공해야 하는 동작이다.

- 사용자는 이메일과 비밀번호로 로그인할 수 있어야 한다.
- 관리자는 강좌를 등록하고 공개할 수 있어야 한다.
- 사용자는 수강 중인 강좌 목록을 조회할 수 있어야 한다.

### 비기능 요구사항

기능을 어떤 품질 수준으로 제공해야 하는지를 정의한다.

| 품질 속성 | 요구사항 예시 |
| --- | --- |
| 성능 | 검색 결과는 2초 안에 표시되어야 한다 |
| 가용성 | 월간 서비스 가용성은 99.9% 이상이어야 한다 |
| 보안 | 비밀번호는 단방향 해시로 저장해야 한다 |
| 사용성 | 주요 기능은 세 단계 이내에 접근할 수 있어야 한다 |
| 변경 용이성 | 결제 수단을 추가할 때 기존 주문 로직의 변경을 최소화해야 한다 |
| 호환성 | 최신 두 개 버전의 주요 브라우저를 지원해야 한다 |

### 제약사항

구현 방법이나 운영 환경의 선택 범위를 제한하는 조건이다.

- 개인정보는 국내 리전에 저장해야 한다.
- 서버 애플리케이션은 Python 3.12 이상을 사용해야 한다.
- 외부 결제는 승인된 결제 대행사 API를 사용해야 한다.

제약사항에는 가능한 한 이유를 함께 기록한다. 근거를 알 수 없는 제약은 상황이 바뀌어도 그대로 유지되기 쉽다.

## 3. 요구사항 개발

요구사항 개발은 필요한 요구사항을 발견하고, 분석하고, 문서화하고, 올바른지 확인하는 과정이다.

```text
도메인 분석
  -> 문제 정의와 범위 설정
  -> 요구사항 추출
  -> 요구사항 분석과 문서화
  -> 요구사항 검증 및 확인
```

각 활동은 한 번만 실행되는 것이 아니다. 검토 과정에서 빠진 이해관계자나 충돌하는 조건을 발견하면 앞 단계로 돌아간다.

## 4. 도메인 분석

도메인은 소프트웨어가 사용되는 업무와 지식의 범위이다. 병원 예약, 온라인 교육, 물류 배송처럼 분야마다 사용하는 용어, 규칙과 예외가 다르다.

도메인 분석에서 확인할 항목은 다음과 같다.

- 주요 사용자와 외부 시스템
- 업무에서 사용하는 핵심 용어
- 현재 업무 절차와 예외 상황
- 데이터의 생성, 변경과 삭제 규칙
- 법률, 보안과 조직 정책
- 시스템과 연결되는 외부 서비스

### 도메인 용어집 예시

| 용어 | 의미 | 비고 |
| --- | --- | --- |
| 강좌 | 하나의 주제로 구성된 교육 단위 | 여러 개의 수업을 포함한다 |
| 수업 | 강좌 안의 개별 학습 콘텐츠 | 영상, 문서 또는 과제이다 |
| 수강 신청 | 사용자가 강좌를 이용할 권한을 얻는 행위 | 결제가 필요할 수 있다 |
| 진도율 | 완료한 수업의 비율 | 계산 기준을 별도로 정의한다 |

같은 용어를 서로 다른 의미로 사용하면 요구사항 전체가 흔들린다. 용어집은 단어의 뜻뿐 아니라 계산 기준과 포함 범위도 기록한다.

## 5. 문제 정의와 범위 설정

문제 정의는 만들 기능을 바로 나열하는 작업이 아니다. 현재 상태와 원하는 상태의 차이를 설명하는 작업이다.

```text
현재 상태
  강좌 문의가 이메일과 메신저로 흩어져 처리 상태를 알기 어렵다.

원하는 상태
  문의를 한곳에 등록하고 접수, 처리 중, 완료 상태를 확인할 수 있다.

포함 범위
  문의 등록, 담당자 배정, 상태 변경, 답변 조회

제외 범위
  실시간 채팅, 전화 상담, 자동 번역
```

범위는 다음 세 요소로 구분하면 명확해진다.

- 포함 범위: 이번 개발에서 제공하는 기능이다.
- 제외 범위: 관련은 있지만 이번 개발에서 제공하지 않는 기능이다.
- 경계: 다른 시스템이나 조직이 책임지는 지점이다.

제외 범위를 기록하지 않으면 관계자마다 포함 여부를 다르게 예상할 수 있다.

## 6. 이해관계자 분석

이해관계자는 시스템의 개발과 운영에 영향을 주거나 시스템의 결과에 영향을 받는 사람과 조직, 외부 시스템이다.

| 이해관계자 | 주요 관심사 |
| --- | --- |
| 최종 사용자 | 기능이 쉽고 정확하게 동작하는가 |
| 운영 담당자 | 상태를 확인하고 문제에 대응할 수 있는가 |
| 개발 담당자 | 요구사항과 인터페이스가 명확한가 |
| 보안 담당자 | 개인정보와 접근 권한이 보호되는가 |
| 고객 지원 | 문의 내용과 처리 이력을 조회할 수 있는가 |
| 외부 결제 시스템 | 정해진 API 계약에 따라 요청을 받는가 |

요구사항을 제시하는 사람과 최종 사용자가 항상 같지는 않다. 발주자의 요청만 듣고 실제 사용자의 업무를 확인하지 않으면 중요한 예외를 놓칠 수 있다.

## 7. 요구사항 추출

요구사항 추출은 이해관계자와 업무 자료에서 필요한 정보를 발견하는 활동이다.

### 인터뷰

관계자와 질문과 답변을 주고받는 방법이다. 목표, 불편과 예외 상황을 깊게 확인할 수 있다.

질문 예시는 다음과 같다.

- 현재 업무는 어떤 순서로 진행되는가
- 가장 자주 발생하는 실패는 무엇인가
- 결과가 올바른지 누가 어떤 기준으로 판단하는가
- 업무가 몰리는 시점과 처리량은 어느 정도인가
- 반드시 유지해야 하는 기존 규칙은 무엇인가

### 관찰

실제 업무 과정을 직접 확인하는 방법이다. 익숙해서 말로 설명하지 않는 절차와 반복 작업을 발견하기 좋다.

### 설문

많은 사람에게 같은 질문을 전달해 경향을 파악하는 방법이다. 깊은 이유를 확인하기 어려우므로 인터뷰와 함께 사용하는 경우가 많다.

### 기존 자료 분석

업무 문서, 기존 화면, 로그, 오류 기록과 고객 문의를 분석하는 방법이다. 현재 규칙을 빠르게 파악할 수 있지만 기존 방식의 문제를 그대로 요구사항으로 받아들이지 않도록 주의한다.

### 워크숍

여러 이해관계자가 한자리에서 요구사항과 우선순위를 논의하는 방법이다. 충돌을 빠르게 확인할 수 있지만 의견이 큰 사람에게 결정이 치우치지 않도록 진행 기준이 필요하다.

### 프로토타입

화면이나 API의 간단한 모형을 만들어 결과를 구체적으로 확인하는 방법이다. 프로토타입이 완성 제품으로 오해되지 않도록 목적과 구현 범위를 구분한다.

## 8. 요구사항 분석

추출한 요구사항은 그대로 확정하지 않는다. 중복, 충돌, 누락과 실현 가능성을 분석해야 한다.

### 우선순위

MoSCoW 방식은 요구사항을 다음 네 단계로 분류한다.

| 구분 | 의미 |
| --- | --- |
| Must | 반드시 제공해야 한다 |
| Should | 중요하지만 대안이 존재한다 |
| Could | 여유가 있을 때 제공한다 |
| Won't | 현재 범위에서는 제공하지 않는다 |

### 충돌 분석

다음 요구사항은 서로 충돌할 수 있다.

- 모든 요청의 상세 로그를 영구 보관한다.
- 개인정보가 포함된 로그는 30일 후 삭제한다.

충돌을 발견하면 보관 대상, 기간, 익명화 조건과 법적 기준을 구체화한다.

### 실현 가능성

기술, 일정, 비용, 운영과 법률 관점에서 구현 가능성을 확인한다. 기술적으로 만들 수 있어도 운영 인력과 절차가 없으면 실현 가능한 요구사항이 아닐 수 있다.

## 9. 요구사항 문서화

좋은 요구사항은 다음 조건을 만족한다.

| 조건 | 확인 질문 |
| --- | --- |
| 명확성 | 한 문장에 여러 해석이 가능한 표현이 없는가 |
| 완전성 | 필요한 조건, 입력과 결과가 포함되었는가 |
| 일관성 | 다른 요구사항과 충돌하지 않는가 |
| 필요성 | 실제 문제 해결에 필요한가 |
| 실현 가능성 | 주어진 제약 안에서 구현할 수 있는가 |
| 검증 가능성 | 성공과 실패를 객관적으로 판단할 수 있는가 |
| 추적 가능성 | 설계, 코드와 테스트에 연결할 수 있는가 |

### 요구사항 문장 형식

```text
[식별자] [주체]는 [조건]에서 [기능]할 수 있어야 한다.
[성공 기준] 결과는 [측정 가능한 조건]을 만족해야 한다.
```

### 요구사항 목록 예시

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| FR-01 | 사용자는 제목과 내용으로 문의를 등록할 수 있어야 한다 | Must |
| FR-02 | 담당자는 문의 상태를 접수, 처리 중, 완료로 변경할 수 있어야 한다 | Must |
| FR-03 | 사용자는 자신의 문의와 답변을 조회할 수 있어야 한다 | Must |
| NFR-01 | 문의 조회 요청의 95%는 2초 안에 응답해야 한다 | Should |
| NFR-02 | 다른 사용자의 문의는 조회할 수 없어야 한다 | Must |
| CON-01 | 문의 내용은 5년 동안 보관해야 한다 | Must |

## 10. 사용자 스토리와 인수 조건

사용자 스토리는 기능의 사용자, 목적과 가치를 짧게 표현한다.

```text
문의 작성자로서
내 문의의 처리 상태를 확인하고 싶다.
그래야 추가 연락이 필요한지 판단할 수 있다.
```

사용자 스토리만으로는 완료 여부를 판단하기 어려우므로 인수 조건을 함께 작성한다.

```text
Given 로그인한 사용자가 자신의 문의를 등록했고
When 문의 상세 화면을 열면
Then 현재 처리 상태와 마지막 변경 시각이 표시된다.
```

- `Given`은 실행 전 조건이다.
- `When`은 사용자의 행동이나 발생한 사건이다.
- `Then`은 관찰 가능한 결과이다.

## 11. 요구사항 검증 및 확인

검증과 확인은 비슷해 보이지만 질문이 다르다.

- 검증(Verification): 요구사항을 명확하고 일관되게 작성했는가를 확인한다.
- 확인(Validation): 요구사항이 실제 사용자의 문제를 해결하는가를 확인한다.

### 검토 체크리스트

- 주체와 대상이 명확한가
- 모호한 표현이 없는가
- 정상 흐름과 주요 예외가 포함되었는가
- 측정 가능한 성공 기준이 있는가
- 다른 요구사항과 충돌하지 않는가
- 범위 밖 항목이 구분되어 있는가
- 관련 이해관계자가 의미와 우선순위에 동의했는가

"충분히 빠르게", "적절한 수준", "필요한 경우" 같은 표현은 판단 기준이 사람마다 달라질 수 있으므로 구체적인 조건으로 바꾼다.

## 12. 요구사항 관리

요구사항은 개발이 시작된 뒤에도 바뀐다. 요구사항 관리는 변경을 막는 활동이 아니라 변경의 이유와 영향을 알고 결정하는 활동이다.

```text
변경 요청
  -> 변경 내용 분석
  -> 영향 범위와 비용 평가
  -> 승인 또는 보류
  -> 요구사항 기준선 갱신
  -> 설계, 구현과 테스트 반영
```

## 13. 요구사항 합의

요구사항 합의는 관계자가 범위, 우선순위와 완료 기준을 공동으로 확인한 상태이다. 모든 의견이 같다는 의미가 아니라 충돌과 제약을 검토한 뒤 이번 버전에서 따를 기준을 정했다는 의미이다.

합의할 항목은 다음과 같다.

- 제공할 기능과 제외할 기능
- 우선순위와 출시 기준
- 비기능 요구사항의 측정 기준
- 외부 시스템과 책임 경계
- 변경 요청의 승인 절차
- 최종 인수 담당자와 인수 기준

## 14. 요구사항 형상관리

요구사항 형상관리는 문서의 버전과 승인 상태를 통제하는 활동이다. 어떤 요구사항 집합이 개발 기준인지 알 수 있어야 한다.

### 기준선

기준선(Baseline)은 검토와 승인을 거쳐 특정 개발 단계의 기준으로 확정한 요구사항 집합이다. 기준선 이후의 변경은 변경 요청과 영향 분석을 거친다.

### 변경 기록 예시

| 항목 | 내용 |
| --- | --- |
| 변경 ID | CR-007 |
| 대상 요구사항 | FR-02 |
| 변경 내용 | 문의 상태에 보류를 추가한다 |
| 변경 이유 | 외부 확인이 필요한 문의를 구분해야 한다 |
| 영향 범위 | 상태 모델, 화면, API, 통계와 테스트 |
| 결정 | 승인 |
| 반영 버전 | 요구사항 기준선 1.2 |

문서 파일명에 `최종`, `진짜최종`, `최종수정`을 붙이는 방식은 기준과 변경 이유를 파악하기 어렵다. 버전, 상태, 변경 이력과 승인 정보를 일관된 방식으로 관리한다.

## 15. 요구사항 이력추적

이력추적은 요구사항이 설계, 구현과 테스트에 어떻게 연결되는지를 기록하는 활동이다.

### 순방향 추적

요구사항이 어떤 설계와 코드, 테스트로 구현되었는지 확인한다.

### 역방향 추적

코드와 테스트가 어떤 요구사항을 위해 존재하는지 확인한다.

### 요구사항 추적표 예시

| 요구사항 | 설계 | 구현 | 테스트 |
| --- | --- | --- | --- |
| FR-01 문의 등록 | UI-01, API-01 | InquiryCreate | TC-01, TC-02 |
| FR-02 상태 변경 | STATE-01, API-02 | InquiryStatusService | TC-03, TC-04 |
| NFR-01 응답 시간 | ARCH-02 | 조회 인덱스, 캐시 | PT-01 |
| NFR-02 접근 제어 | SEC-01 | AuthorizationPolicy | ST-01, ST-02 |

추적표를 이용하면 구현되지 않은 요구사항, 요구사항이 없는 코드와 테스트가 빠진 기능을 찾을 수 있다.

## 16. 요구사항 정의서 기본 틀

```text
1. 문서 정보
   - 문서 버전
   - 상태
   - 작성자와 승인자

2. 목적과 배경
   - 해결할 문제
   - 기대 효과

3. 범위
   - 포함 범위
   - 제외 범위
   - 외부 시스템 경계

4. 용어 정의

5. 이해관계자

6. 기능 요구사항

7. 비기능 요구사항

8. 제약사항

9. 인수 조건

10. 추적표와 변경 이력
```

## 핵심 정리

- 요구사항은 기능과 품질 조건을 검증 가능한 기준으로 표현한 것이다.
- 도메인 용어와 문제 범위를 먼저 정해야 기능 목록이 흔들리지 않는다.
- 추출한 요구사항은 충돌, 누락, 우선순위와 실현 가능성을 분석해야 한다.
- 검증은 문서의 품질을, 확인은 실제 문제 해결 여부를 점검한다.
- 요구사항 변경은 기준선, 영향 분석과 이력추적을 통해 관리한다.

## 확인 문제

1. 기능 요구사항과 비기능 요구사항의 차이를 설명한다.
2. "화면이 빠르게 열려야 한다"를 검증 가능한 요구사항으로 바꾼다.
3. 요구사항 기준선이 필요한 이유를 설명한다.
4. 순방향 추적과 역방향 추적의 차이를 설명한다.
