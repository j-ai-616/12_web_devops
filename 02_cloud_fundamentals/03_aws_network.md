# AWS 네트워크 기초

## 학습 목표

- VPC, 서브넷, 인터넷 게이트웨이, 라우팅 테이블의 관계를 설명할 수 있다.
- 퍼블릭 IP, 퍼블릭 DNS와 프라이빗 IP를 구분할 수 있다.
- 보안 그룹에서 필요한 포트만 허용할 수 있다.
- EC2와 RDS 사이의 안전한 접근 규칙을 설계할 수 있다.

## 1. 요청이 서버까지 가는 경로

브라우저에서 EC2의 퍼블릭 DNS를 열면 요청은 다음 경로를 지난다.

```text
브라우저
  -> 인터넷
  -> 인터넷 게이트웨이
  -> VPC 라우팅 테이블
  -> 퍼블릭 서브넷
  -> EC2 보안 그룹
  -> EC2의 Nginx 80번 포트
```

이 경로 중 하나라도 연결되지 않으면 요청이 도착하지 않는다. 애플리케이션 오류와 네트워크 오류를 구분하려면 어느 단계까지 도달했는지 확인해야 한다.

네트워크는 컴퓨터 사이에서 데이터를 전달하는 규칙과 경로이다. 브라우저는 DNS 이름을 IP 주소로 바꾸고, IP 주소로 서버를 찾은 뒤 포트 번호로 서버 안의 프로그램을 찾는다.

```text
DNS 이름 -> IP 주소 -> 포트 -> 실행 중인 프로그램
```

예를 들어 `http://ec2-...compute.amazonaws.com:80`에서 DNS 이름은 EC2를 찾는 데 사용되고, `80`은 EC2 안의 Nginx를 찾는 데 사용된다. 주소가 맞아도 보안 그룹이 포트를 막거나 프로그램이 실행 중이 아니면 접속할 수 없다.

## 2. VPC

VPC는 AWS 계정 안에 만드는 논리적으로 격리된 네트워크이다. IP 주소 범위를 CIDR 표기법으로 정의한다.

```text
10.0.0.0/16
```

`/16`은 앞의 16비트를 네트워크 영역으로 사용한다는 뜻이다. 이 범위 안에서 더 작은 서브넷을 나눈다.

수업에서는 시간을 줄이고 계정마다 같은 조건을 만들기 위해 기본 VPC를 사용한다. 기본 VPC도 VPC의 구성 요소를 확인하는 데 충분하다. 운영 환경에서는 목적에 맞는 사용자 정의 VPC와 퍼블릭·프라이빗 서브넷을 설계한다.

## 3. 서브넷

서브넷은 VPC의 IP 범위를 가용 영역별로 나눈 네트워크 구간이다.

퍼블릭 서브넷과 프라이빗 서브넷은 이름이 아니라 라우팅으로 구분한다.

- 퍼블릭 서브넷은 인터넷 게이트웨이로 향하는 경로가 있다.
- 프라이빗 서브넷은 인터넷에서 직접 들어오는 경로가 없다.

수업에서는 EC2를 퍼블릭 서브넷에 두고 퍼블릭 IPv4를 할당한다. RDS는 외부 공개를 끄고 EC2를 통해서만 접근한다.

## 4. 인터넷 게이트웨이와 라우팅 테이블

인터넷 게이트웨이는 VPC와 인터넷을 연결한다. 라우팅 테이블은 목적지 주소에 따라 패킷을 어디로 보낼지 결정한다.

퍼블릭 서브넷의 대표적인 기본 경로는 다음과 같다.

```text
목적지: 0.0.0.0/0
대상: 인터넷 게이트웨이
```

`0.0.0.0/0`은 모든 IPv4 목적지를 뜻한다. 라우팅의 `0.0.0.0/0`과 보안 그룹 소스의 `0.0.0.0/0`은 위치에 따라 의미가 다르다. 보안 그룹에서 사용하면 전 세계 모든 IPv4 주소의 접근을 허용한다.

## 5. 퍼블릭 IP와 프라이빗 IP

| 구분 | 용도 | 특징 |
| --- | --- | --- |
| 프라이빗 IP | VPC 내부 통신 | 인터넷에서 직접 접근할 수 없다. |
| 퍼블릭 IPv4 | 인터넷과 통신 | EC2를 중지 후 시작하면 바뀔 수 있다. |
| 퍼블릭 IPv4 DNS | 퍼블릭 IPv4를 가리키는 AWS 제공 호스트 이름 | 도메인을 구매하지 않아도 사용 가능하지만 연결된 퍼블릭 IPv4가 바뀌면 함께 바뀐다. |
| Elastic IP | 고정 퍼블릭 IPv4 | 사용 여부와 관계없이 퍼블릭 IPv4 요금이 발생한다. |

EC2를 생성하면 다음과 비슷한 `Public IPv4 DNS`를 AWS 콘솔에서 확인할 수 있다.

```text
ec2-3-35-100-20.ap-northeast-2.compute.amazonaws.com
```

이 주소는 AWS가 제공하므로 별도 도메인을 구매할 필요가 없다. 수업에서는 숫자 IP보다 이 퍼블릭 DNS를 SSH, Django `ALLOWED_HOSTS`, 브라우저 주소에 공통으로 사용한다.

다만 퍼블릭 DNS는 현재 퍼블릭 IPv4를 바탕으로 만들어진 주소이다. EC2를 중지한 뒤 다시 시작해 새 퍼블릭 IPv4를 받으면 퍼블릭 DNS도 바뀐다. 처음 생성한 EC2를 실행 상태로 유지해 주소가 바뀌는 상황을 피한다.

고정 주소가 꼭 필요한 운영 서비스라면 Elastic IP나 자체 도메인, 로드 밸런서를 검토한다. EC2를 매일 중지해야 하는 수업이라면 Elastic IP를 연결하는 방법도 있다. 다만 Elastic IP는 EC2가 중지된 동안에도 퍼블릭 IPv4 요금이 계속되고 마지막에 별도로 해제해야 하므로 이번 수업에서는 사용하지 않는다.

## 6. 포트와 프로토콜

하나의 서버는 포트 번호로 여러 서비스를 구분한다.

프로토콜은 통신 규칙이고 포트는 같은 컴퓨터 안에서 통신 대상을 구분하는 번호이다. HTTP와 SSH는 서로 다른 규칙을 사용하므로 같은 EC2에서도 Nginx는 80번, SSH 서버는 22번 포트를 사용한다.

| 포트 | 프로토콜/서비스 | 수업 사용 방법 |
| ---: | --- | --- |
| 22 | SSH | 자신의 공인 IP에서만 허용한다. |
| 80 | HTTP | 웹 확인을 위해 외부에 허용한다. |
| 443 | HTTPS | 인증서를 적용할 때 사용한다. |
| 5432 | PostgreSQL | EC2 보안 그룹에서만 RDS로 접근한다. |
| 8000 | Gunicorn/Django | 외부에 열지 않고 EC2 내부에서만 사용한다. |

## 7. 보안 그룹

보안 그룹은 인스턴스나 데이터베이스 네트워크 인터페이스에 적용하는 상태 저장 방화벽이다. 요청을 허용하면 그 응답 트래픽은 별도의 아웃바운드 규칙 없이 돌아올 수 있다.

### EC2 보안 그룹 설계

| 유형 | 포트 | 소스 | 이유 |
| --- | ---: | --- | --- |
| SSH | 22 | 내 IP | 관리자 접속을 제한한다. |
| HTTP | 80 | `0.0.0.0/0` | 웹 실습 결과를 외부에서 확인한다. |
| HTTPS | 443 | 필요할 때 `0.0.0.0/0` | TLS를 적용할 때 사용한다. |

ICMP와 8000번 포트는 이 실습에서 열 필요가 없다.

### RDS 보안 그룹 설계

| 유형 | 포트 | 소스 | 이유 |
| --- | ---: | --- | --- |
| PostgreSQL | 5432 | EC2 보안 그룹 ID | 지정한 EC2에서만 DB에 접근한다. |

RDS 규칙의 소스에 EC2의 퍼블릭 IP를 넣는 것이 아니라 EC2에 연결된 보안 그룹을 지정한다. EC2 인스턴스가 바뀌어도 같은 보안 그룹을 사용하면 규칙을 다시 만들 필요가 없다.

## 8. 네트워크 ACL과 보안 그룹 비교

| 항목 | 보안 그룹 | 네트워크 ACL |
| --- | --- | --- |
| 적용 위치 | 네트워크 인터페이스 | 서브넷 |
| 상태 저장 | 상태 저장 | 상태 비저장 |
| 규칙 | 허용 규칙 | 허용과 거부 규칙 |
| 수업 사용 | 직접 설정 | 기본값 확인 |

초급 실습에서는 보안 그룹을 중심으로 사용한다. 네트워크 ACL을 임의로 변경하면 응답용 임시 포트까지 고려해야 하므로 기본값을 유지한다.

## 9. 로컬 네트워크 정보 확인

WSL에서 다음 명령을 실행한다.

```bash
# WSL 네트워크 인터페이스와 사설 IP 주소를 확인한다.
ip address

# 운영체제가 목적지별로 사용하는 라우팅 경로를 확인한다.
ip route

# 외부 서비스에서 보이는 현재 공인 IP 주소를 확인한다.
curl -4 https://checkip.amazonaws.com
```

마지막 명령의 결과는 EC2 보안 그룹에서 SSH 소스를 `내 IP`로 설정할 때 참고한다. 회사나 교육장 네트워크는 공인 IP가 바뀌거나 프록시를 사용할 수 있다.

## 10. 장애를 찾는 순서

웹 페이지가 열리지 않을 때 다음 순서로 확인한다.

1. EC2가 실행 중인가
2. 퍼블릭 IPv4가 있는가
3. 서브넷 라우팅에 인터넷 게이트웨이 경로가 있는가
4. 보안 그룹이 80번 포트를 허용하는가
5. EC2 운영체제에서 Nginx가 실행 중인가
6. Nginx가 요청을 Django로 전달하는가
7. Django 프로세스가 `127.0.0.1:8000`에서 응답하는가

아래쪽부터 무작정 설정을 바꾸지 않고 바깥에서 안쪽으로 범위를 좁힌다.
